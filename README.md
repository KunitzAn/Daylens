# Daylens

Личный трекер настроения (в духе Daylio): раз в конце дня — шкала настроения + набор
эмодзи по сферам жизни. PWA с полноценной офлайн-работой.

Этот файл — договорённости из планирующего чата. Реализация ещё не начата.

## Идея

- Открывается ~1 раз в день, вечером
- Основное действие: тронуть общую шкалу настроения + отметить эмодзи по сферам
  (сон, работа, спорт, люди и т.п. — набор сфер кастомизируемый)
- Данные копятся локально на устройстве и синхронизируются с сервером

## Почему PWA, а не Telegram Mini App

Раньше уже пробовала PWA и словила проблему: без интернета приложение не
открывалось "с нуля", если было закрыто. Причина почти наверняка в том, что
service worker не прекэшировал app shell, а тянул его из сети при каждом
холодном старте.

Решение — **local-first PWA**:
- `vite-plugin-pwa` (Workbox), `registerType: 'autoUpdate'` — весь app shell
  (HTML/CSS/JS/иконки) кэшируется **при установке**, не при первом заходе
- `navigateFallback` на закэшированный `index.html` — офлайн-открытие работает,
  даже если приложение было закрыто и телефон вообще без сети
- Данные хранятся не в памяти вкладки, а в IndexedDB (Dexie.js) — источник
  правды на устройстве, сервер нужен только для бэкапа/синка между устройствами

Telegram Mini App отклонили: та же ахиллесова пята (вебвью не гарантированно
открывается офлайн с нуля) + нет отдельной иконки на экране, это чат внутри бота.

## Стек

- **Frontend:** Vue 3 + TypeScript + Vite + Tailwind
- **PWA:** `vite-plugin-pwa` (Workbox) — precache shell, offline fallback,
  позже — web push
- **Локальные данные:** IndexedDB через Dexie.js
- **Backend:** Cloudflare Pages Functions (см. паттерн в `english-lexicon-trainer`)
- **БД:** Neon Postgres + Drizzle
- **Хостинг:** Cloudflare Pages, `daylens.kunitcan.online`
- **Email:** Resend — free tier 3000 писем/мес, 100/день, с запасом хватает

## Функционал

### MVP

**Запись дня** — главный экран, открывается сразу на сегодняшнем дне

- Общая шкала настроения: **7 уровней** (1 — худший, 7 — лучший), у каждого свой
  эмодзи и цвет. Выбор одним тапом — это основное и единственное обязательное
  действие записи
- Сферы жизни: эмодзи-теги (сон, работа, спорт, люди…), отмечаются тапом по
  принципу вкл/выкл, **без отдельной оценки у сферы**. Можно отметить сколько
  угодно сфер или ни одной
- Заметка: свободный текст, опционально
- Одна запись на календарный день. Повторное открытие того же дня — правка
  существующей записи, а не создание второй
- Граница дня — по локальному времени устройства (без привязки к UTC)
- Заполнение задним числом разрешено для **любого** прошлого дня. Будущие дни
  недоступны

**Сферы — настройки** (полный CRUD с первого дня)

- Создание своей сферы: название + эмодзи
- Редактирование названия и эмодзи
- Удаление — **мягкое** (`archivedAt`): сфера пропадает из выбора, но уже
  сохранённые записи её не теряют. Иначе удаление сферы задним числом ломает всю
  накопленную статистику
- Ручная сортировка — порядок в списке задаёт пользователь под свою частоту
  использования
- При первом запуске набор предзаполняется дефолтным пресетом, чтобы пустой
  экран настроек не стоял между юзером и первой записью. Пресет: 😴 Сон,
  💼 Работа, 🏃 Спорт, 👥 Люди, 📚 Учёба, 🌿 Отдых

**Календарь-heatmap**

- Месячная сетка, цвет клетки = уровень настроения дня (7 градаций)
- Пустая клетка = день без записи; тап открывает форму записи за этот день
- Тап по заполненной клетке — просмотр и правка
- Переключение между месяцами

**Статистика**

- График настроения по дням за период (неделя / месяц)
- Среднее настроение за период
- Частота сфер за период: сколько раз каждая отмечена
- Сколько дней из периода заполнено

**Вход**

- Magic link на email через Resend, без пароля
- Долгоживущая сессия: вечерний ритуал не должен упираться в повторный вход
- Протухшая сессия или офлайн **не блокируют запись** — приложение открывается и
  пишет локально, синк подождёт восстановления доступа

**Синхронизация**

- Запись сначала в IndexedDB, UI отвечает мгновенно и сети не ждёт
- Очередь несинхронизированного пушится при появлении сети
- Конфликты — last-write-wins по `updatedAt`

### Позже (не в MVP)

- Push-напоминание отметить настроение вечером (Web Push, свой VAPID)
- Корреляция настроения со сферами («в дни со спортом настроение в среднем выше
  на X»)
- Экспорт данных (JSON/CSV)
- Мультиустройственный вход (см. авторизацию)
- Серии заполненных дней (streak-и)
- Поиск по заметкам

## Модель данных — черновик

```
users
  id, email, createdAt

spheres
  id, userId, name, emoji, sortOrder, archivedAt, updatedAt

entries
  id, userId, date (YYYY-MM-DD, локальная дата), mood (1–7), note,
  createdAt, updatedAt, deletedAt

entry_spheres
  entryId, sphereId        // сфера — просто отметка, значения нет
```

- `date` хранится строкой `YYYY-MM-DD`, а не timestamp: день — это календарная
  сущность в таймзоне юзера, а не момент времени. Уникальный индекс
  `(userId, date)` даёт правило «одна запись в день» на уровне БД
- Удаления везде мягкие (`deletedAt` / `archivedAt`) — иначе синк не сможет
  отличить «удалено на другом устройстве» от «ещё не доехало сюда»
- В IndexedDB (Dexie) та же форма + локальное поле грязности записи для очереди
  синка

## Авторизация

Нужно простое решение с понятным восстановлением доступа. Решили: **magic link
по email через Resend**, без пароля — нечего забывать и восстанавливать, вход
и восстановление это один и тот же флоу.

- Таблица `users` заложена с первого дня (даже при одном пользователе) —
  добавить второго юзера потом = просто ещё одна строка
- Telegram-логин не делаем основным, но архитектурно не закрываем от себя
  возможность добавить как второй способ входа
- Passkey (Face ID) — рассматривали, отложили: требует отдельной библиотеки
  (например SimpleWebAuthn), таблицы credential'ов и WebAuthn-церемонии
  регистрации/входа — лишний слой сложности для первой версии. Можно добавить
  позже как апгрейд, ничего не переделывая
- Rate-limit на отправку magic link закладываем с MVP (по IP и/или email) —
  защита от абьюза (спам чужих почт письмами) и экономия квоты Resend
  (100 писем/день)

## Push-уведомления

Не в MVP. Когда дойдём: нативный **Web Push API** (свой VAPID-ключ) вместо
Firebase — меньше внешних зависимостей, не завязано на Google-аккаунт. Firebase
(FCM) тоже сработал бы (с iOS 16.4+ он под капотом использует тот же стандарт
Web Push и работает в PWA, добавленной на экран), но смысла тянуть отдельный
Firebase-проект ради этого нет.

## Офлайн-архитектура — сводка

| Слой | Что кэшируется | Чем |
|---|---|---|
| App shell (UI) | HTML/CSS/JS, иконки | Workbox precache при установке |
| Данные | Все записи настроения | IndexedDB (Dexie) — пишутся сразу локально |
| Синхронизация | Очередь несинхронизированных записей | Background Sync API там, где есть, + fallback-ретрай на `online`/`visibilitychange` |
| Конфликты | Юзер один → last-write-wins по `updatedAt` | сложный merge не нужен |

Приложение работает полностью автономно, сервер нужен только для
бэкапа/синхронизации, не для самой функции логирования.

Основной сценарий использования — iOS Safari, где Background Sync API не
поддерживается, поэтому fallback на `online`/`visibilitychange` — не опция,
а обязательный путь синка, а не просто подстраховка.

Известный trade-off: last-write-wins безопасен, пока устройство одно. Когда
появится мультиустройственный вход, две офлайн-правки одного дня на разных
устройствах молча схлопнутся в последнюю — потеряется, например, дописанная
заметка. Осознанно принято на MVP, пересмотреть при работе над мультиустройством.

2. Dexie-слой и локальная модель данных
3. Экран записи дня (шкала + сферы + заметка) поверх локальных данных, без бэка
4. Календарь-heatmap и статистика — тоже на локальных данных
5. Сферы: CRUD и настройки
6. Бэкенд: схема в Neon + Drizzle, magic link с rate-limit'ом, синк-эндпоинты
7. Очередь синка и fallback-ретрай

Шаги 1–5 дают полностью рабочее приложение без сервера вообще — это и есть
проверка тезиса local-first.
