# Daylens

Личный трекер настроения (в духе Daylio): раз в конце дня — шкала настроения
(эмодзи или картинками) + отметки по сферам жизни. PWA с полноценной
офлайн-работой.

Этот файл — договорённости из планирующего чата. Локальная часть (запись
дня, разделы/теги, наборы настроений) реализована и работает без бэкенда;
авторизация и синхронизация — следующий этап, см. «Следующий шаг».

## Идея

- Открывается ~1 раз в день, вечером
- Основное действие: тронуть общую шкалу настроения + отметить эмодзи по сферам
  (сон, работа, спорт, люди и т.п. — набор сфер кастомизируемый)
- Данные копятся локально на устройстве и синхронизируются с сервером

## Почему PWA, а не Telegram Mini App

Раньше уже пробовала PWA и словила проблему: без интернета приложение не
открывалось "с нуля", если было закрыто. Причина почти наверняка в том, что
service worker не прекэшировал app shell, а тянул его из сети при каждом
холодном старте.

Решение — **local-first PWA**:
- `vite-plugin-pwa` (Workbox), `registerType: 'autoUpdate'` — весь app shell
  (HTML/CSS/JS/иконки) кэшируется **при установке**, не при первом заходе
- `navigateFallback` на закэшированный `index.html` — офлайн-открытие работает,
  даже если приложение было закрыто и телефон вообще без сети
- Данные хранятся не в памяти вкладки, а в IndexedDB (Dexie.js) — источник
  правды на устройстве, сервер нужен только для бэкапа/синка между устройствами

**Сплэш-скрин при холодном запуске на iOS**, а не системная белая заглушка:
- `<link rel="apple-touch-startup-image">` на 11 реальных размеров экрана
  iPhone (CSS-размер × DPR × ориентация — iOS сам не умеет собрать сплэш из
  манифеста, картинку нужно отдать под точный пиксельный размер каждого
  устройства). Марка на сплэше — тот же `apple-touch-icon.png`, что уже в
  манифесте, не отдельная картинка: увеличенная и на фирменном фоне
  (`#faf9f7`), скруглённая под тот же радиус, что и сама иконка на
  домашнем экране
- Генерируются `scripts/generate-splash.mjs` (sharp) из одного источника —
  при смене иконки достаточно перегенерировать, а не рисовать 11 картинок
  руками. Результат — `public/splash/*.png`, в репозитории, не в `.gitignore`:
  Cloudflare Pages их не соберёт заново, статика должна доехать как есть
- **Не в прекэше.** Обычный `globPatterns: '**/*.png'` затащил бы туда все
  11 вариантов (~4 МБ), хотя реальному устройству подходит ровно один —
  остальные десять iOS никогда не запросит: он выбирает картинку по media
  query в момент «Добавить на экран Домой» и после этого хранит свою копию
  сам, к нашему Service Worker больше не обращаясь. `globIgnores: ['splash/**']`
  в `vite.config.ts` держит их обычными статик-файлами вне install-time кэша
- Заглушка нужна и после того, как иконку от iOS сменяет наш собственный
  экран: `main.ts` перед `mount()` ждёт `checkSession()`/`runSync()`, и
  пауза между открытием и первым кадром приложения реальная и на iOS,
  поверх системного сплэша, и тем более на Android/десктопе, где
  `apple-touch-startup-image` не работает вообще. Поэтому в `index.html`
  ещё и инлайновая заглушка (`#app-loading`, та же иконка с лёгкой
  пульсацией) — стилями прямо в `<head>`, без ожидания CSS-бандла, и Vue
  при `mount('#app')` заменяет её обычной заменой содержимого узла

Telegram Mini App отклонили: та же ахиллесова пята (вебвью не гарантированно
открывается офлайн с нуля) + нет отдельной иконки на экране, это чат внутри бота.

## Стек

- **Frontend:** Vue 3 + TypeScript + Vite + Tailwind
- **PWA:** `vite-plugin-pwa` (Workbox) — precache shell, offline fallback,
  позже — web push
- **Локальные данные:** IndexedDB через Dexie.js
- **Backend:** Cloudflare Pages Functions (см. паттерн в `english-lexicon-trainer`)
- **БД:** Neon Postgres + Drizzle
- **Хостинг:** Cloudflare Pages, `daylens.kunitcan.online`
- **Email:** Resend — free tier 3000 писем/мес, 100/день, с запасом хватает

## Функционал

### MVP

**Навигация** — четыре основных экрана, таб-бар внизу (как в Daylio)

| Таб | Маршрут | Что там |
|---|---|---|
| Записи | `/` (по умолчанию) | Лента последних записей |
| Статистика | `/stats` | Графики по дням, неделям и месяцам |
| Календарь | `/calendar` | Месячная сетка-heatmap |
| Больше | `/more` | Настройки: разделы, наборы настроений, аккаунт |

Плюс плавающая кнопка «+» — общая для `TabBar`, поэтому работает одинаково на
всех четырёх табах. Открывает не сразу сегодняшний день, а шторку **«За какой
день?»** (`PickDaySheet`): Сегодня / Вчера / любая другая дата — «Сегодня»
первым пунктом, так что обычный ежедневный путь не стал длиннее чем на один
лишний тап. Раньше это же на ленте дублировала отдельная маленькая кнопка в
шапке — убрали, одна точка входа вместо двух с одинаковым смыслом. Форма
записи (`/day/:date`) и экраны настроек открываются **поверх**, с кнопкой
«назад», и таб-бар на них не показывается — иначе непонятно, где ты находишься.

**Лента записей** — главный экран, то, что видно при открытии приложения

- Карточки по дням, сверху самые свежие. Подгрузка порциями по скроллу —
  через год ведения дневника список не должен тормозить
- В карточке: кружок с эмодзи/картинкой настроения, день недели и дата,
  время (берём из `createdAt`), название уровня настроения, отмеченные теги,
  заметка, «×» для удаления записи
- Удаление — **мягкое** (`deletedAt`), как и везде: строка остаётся, иначе
  синк не отличит «удалено на другом устройстве» от «ещё не доехало».
  Из-за этого удалённая строка продолжает держать за собой дату (в Dexie на
  `date` уникальный индекс), поэтому заполнение того же дня заново не
  создаёт вторую запись, а **оживляет** старую — форма при этом открывается
  пустой, для пользователя день удалён начисто
- **Цвет карточки — по настроению дня, яркий.** Иконки тегов внутри — в
  цветах своих разделов, но приглушённее, чтобы не спорить с основным цветом
  карточки
- Тап по карточке — открыть этот день на редактирование

**Запись дня** (`/day/:date`) — открывается по «+» или тапу по дню в ленте/календаре

- Общая шкала настроения: **7 уровней** (1 — худший, 7 — лучший), у каждого свой
  эмодзи и цвет. Выбор одним тапом — это основное и единственное обязательное
  действие записи
- Сферы жизни — двухуровневая структура: **разделы** (Сон, Работа, Спорт…, у
  каждого свой цвет) содержат **теги** (конкретные события: «Тренировка»,
  «Встречи», «Друзья»…, у каждого своя иконка). Теги отмечаются тапом по
  принципу вкл/выкл, **без отдельной оценки**. Выбранный тег заливается цветом
  своего раздела — невыбранный просто обведён им. Можно отметить сколько
  угодно тегов или ни одного
- Заметка: свободный текст, опционально
- Одна запись на календарный день. Повторное открытие того же дня — правка
  существующей записи, а не создание второй
- Граница дня — по локальному времени устройства (без привязки к UTC)
- Заполнение задним числом разрешено для **любого** прошлого дня. Будущие дни
  недоступны
- У каждого раздела — «+» для быстрого добавления нового тега **прямо
  отсюда**, не уходя в настройки: «вспомнил про действие в момент записи»
  — самый частый повод завести новый тег, гонять за этим в настройки глупо.
  Правка существующих действий (название, иконка, скрыть) — тем же приёмом:
  **долгое нажатие** на плитку тега открывает лёгкий лист редактирования, не
  уходя с экрана записи. На pointerdown/up/move (не отдельный тачевент — тогда
  срабатывает и на мыши в браузере), с порогом сдвига, чтобы случайный свайп
  ленты не триггерил редактирование. Полное управление разделами (создание,
  цвет, сортировка) всё равно живёт в «Больше» → «Настройки»

**Сферы — настройки** (CRUD реализован, живёт в «Больше» → «Настройки»)

- Добавление и редактирование раздела открывает отдельный экран (`/categories/new`
  и `/categories/:id/edit`, vue-router): название, цвет (`<input type="color">`)
  и список тегов внутри — с этого же экрана можно добавлять/удалять/переименовывать
  теги и менять им иконку, всё сохраняется одним тапом на «Сохранить»
- Пользователь создаёт свои разделы (название + цвет) и свои теги внутри них
  (название + иконка)
- Иконки тегов — открытый набор **Lucide** (`@lucide/vue`, MIT, без
  атрибуции), однотонные SVG на `currentColor`, красятся в цвет раздела.
  Не Flaticon/Icons8: их бесплатные иконки требуют атрибуции или платной
  подписки для использования в приложении, и массово выгрузить их нельзя —
  нет открытого доступа для этого
- В пикере иконок — 245 иконок (каждое имя явно проверено на существование
  в `@lucide/vue` перед добавлением, `src/lib/icons.ts`), разложенных по 12
  темам. Группировка не косметическая: имена у Lucide английские, а ищет их
  человек по-русски, и подпись группы — это и есть русский ключ поиска
  («сон», «привыч»); английские имена ищутся по-прежнему. Плоским списком
  на 245 иконок сетка в 6 колонок уже не листается
- Удаление — **мягкое** (`archivedAt`) и для разделов, и для тегов: пропадают
  из выбора, но уже сохранённые записи их не теряют. Иначе удаление задним
  числом ломает накопленную статистику
- Ручная сортировка — порядок разделов и тегов внутри них задаёт пользователь
- При первом запуске набор предзаполняется дефолтным пресетом (6 разделов ×
  4 тега — Сон/Работа/Спорт/Люди/Учёба/Отдых), чтобы пустой экран не стоял
  между юзером и первой записью

**Цвета настроений (палитры)** — «Больше» → «Цвета настроений»

- Цвет уровня настроения — не константа в коде, а **активная палитра**:
  7 цветов, от худшего уровня к лучшему. Из неё красятся карточки в ленте,
  клетки календаря и (дальше) график статистики
- Шесть системных палитр: Классическая, Пастельная, Глубокая, Яркая
  (розовый ↔ голубой), Телепузики (фиолетовый → жёлтый → зелёный, по цветам
  одноимённого набора настроений, но разведён по 7 различимым оттенкам —
  просто взятые 4 цвета персонажей на диверигрующую шкалу не легли бы) и
  Неоновая радуга (красный → жёлтый → лаймовый → голубой → розовый, полный
  спектр, каждый оттенок на пределе насыщенности)
- Шкала настроения — **диверигрующая**: плохое и хорошее это два разных
  тона, а «нормально» посередине нейтральное. Отсюда правило сборки
  палитр: светлота растёт от края к середине и падает обратно — тогда
  шкала читается как градиент даже в оттенках серого и при дальтонизме.
  Проверяется скриптом (монотонность светлоты по плечам + ΔE соседних
  пар), а не на глаз: в первой версии «Классической» уровни 6 и 7
  различались на ΔE 7.7 — два почти неразличимых зелёных, пришлось
  переделать
- **«Нейтральный» ≠ «серый».** Цвет с хромой около нуля читается как
  серый независимо от оттенка под ним, а на графике статистики к
  середине шкалы стягивается больше всего значений (это и есть медиана)
  — так пять из шести системных палитр превращали статистику в ряд
  одинаковых серых столбиков. Починено добавлением второй проверки в тот
  же скрипт: у каждого уровня 4 теперь хрома выше порога, но он всё
  равно самый светлый в семёрке — оттенок тёплый или холодный под стать
  краям палитры, а не нейтральность через обесцвечивание. Заодно тем же
  проходом поправлены две пары, найденные скриптом по дороге, а не
  специально: в «Пастельной» и «Глубокой» уровни 5 и 6 были почти
  неразличимы (ΔE 7.8 и 4.5)
- Цвет текста поверх плашки настроения (цифра в календаре) считается от
  яркости фона, а не прибит белым: палитры пользователь задаёт сам, и на
  светлой палитре белые цифры просто исчезли бы
- Свои палитры: название + по цвету на каждый из 7 уровней, каждый цвет —
  системный пикер со всем спектром (`<input type="color">`). Новая палитра
  стартует от классической: подвинуть готовые цвета удобнее, чем набирать
  семь штук с нуля
- Любую палитру можно **скопировать** (`/mood-palettes/new?from=<id>`).
  Для системных это единственный способ их «поправить»: сами они константы
  в коде. Копия существует только в форме — пока не нажали «Сохранить»,
  в списке ничего не появляется, так что отменённая копия не оставляет мусора
- Только что сохранённая палитра сразу становится активной. Удаление
  активной палитры молча откатывает на системную — иначе приложение
  осталось бы со ссылкой на несуществующую

**Наборы настроений**

- Общая шкала настроения (7 уровней) может отображаться не эмодзи, а
  картинками — пользователь выбирает один из **системных наборов**,
  идущих в комплекте с приложением, либо свой набор из эмодзи
- Экран `/mood-sets`: системные сверху, свои — снизу с «+ Свой набор»,
  тап выбирает активный — хранится в Dexie (`settings`, не localStorage,
  это пользовательская настройка, которая должна уезжать на сервер)
- Формат файлов системного картиночного набора — см.
  `public/mood-sets/README.md` (папка на набор, `1.png`…`7.png`, квадратные)
- **Свои наборы — из эмодзи**, не картинок: 7 слотов, каждый — эмодзи-пикер
  на ~100 мордочек (`src/lib/moodEmojis.ts`, только Smileys & Emotion, без
  жестов). Хранятся в отдельной таблице Dexie `moodEmojiSets`
  (`MoodEmojiSet`), а не как ещё один системный набор — потому что их
  список пользователю не известен заранее, как и с `moodPalettes`
- Любой набор — свой или системный эмодзи-набор — можно **скопировать**
  (`/mood-sets/new?from=<id>`), тем же приёмом, что и палитры. У
  картиночного системного набора (Телепузики) кнопки копирования нет:
  своих файлов у копии не было бы
- Загрузка своих картинок с обрезкой под квадрат и публичные наборы других
  пользователей — сознательно отложены, см. «Позже»

**Календарь-heatmap**

- Месячная сетка (неделя с понедельника), цвет клетки = уровень настроения
  дня (7 градаций), внизу легенда «хуже → лучше»
- Пустая клетка = день без записи; тап открывает форму записи за этот день
- Тап по заполненной клетке — просмотр и правка
- Сегодняшний день обведён рамкой, будущие дни приглушены и не нажимаются
- Переключение между месяцами (арифметика месяцев отдельно проверена на
  переходах через год и на високосном феврале)

**Статистика**

- Масштаб: **Дни / Недели / Месяцы** — 14 дней, 12 недель, 12 месяцев.
  Столбик = период, высота и цвет = среднее настроение за него
- **Тап по столбику выбирает период**, и всё ниже пересчитывается на него:
  плашки и список действий. Это и есть «посмотреть настроение за неделю
  (месяц)» — отдельного экрана не нужно. Крестик снимает выбор
- Текущая неделя и текущий месяц обрезаются по сегодняшнему дню, иначе
  «заполнено 5/30» первого числа выглядело бы как провал
- Плашки: среднее настроение — **иконкой набора на плашке цвета уровня**,
  не числом (цифра «4.0» в цвете нейтральной середины читалась как
  выключенная), и заполненность «9/14»
- **Период без записей не рисуется нулём** — пустое место, иначе
  «не записал» и «было ужасно» выглядели бы одинаково. А у столбика есть
  тонкий контур: середина дивергирующей палитры почти белая (так и
  задумано), и без обводки нейтральный день на белой карточке пропал бы
- Подписи периодов — через равные промежутки и без обрезки: колонка уже
  подписи, но соседние пустые, и текст свободно в них выходит
- «Действия за период»: топ-8 тегов, полосы в цвете своего раздела +
  счётчик, кнопка «Показать все» для полного списка

**Вход** (детали и разбор пароль vs код — в разделе «Авторизация» ниже)

- Код из 6 цифр на email через Resend, без пароля. **Не кликабельная ссылка**
  — на проде поймали, что Resend (через AWS SES) оборачивает ссылки в
  свой click-tracking редирект (`r.<region>.awstrack.me`), и этот
  промежуточный хост сам иногда рвёт соединение — ссылка на верифицированный
  домен ломалась не по нашей вине и не лечилась через настройки трекинга в
  дашборде Resend. Код руками вводится в форму — ломать нечему, нет URL,
  который можно перехватить или на который наткнётся сканер безопасности
  почтового клиента
- Долгоживущая сессия (180 дней) — специально, чтобы **вход на новом
  устройстве** был одноразовым действием, а не ежедневным. Это же и ответ
  на многоустройство: вводишь почту → код из письма → сессия на этом
  устройстве
- Протухшая сессия или офлайн **не блокируют запись** — приложение открывается и
  пишет локально, синк подождёт восстановления доступа

**Синхронизация**

- Запись сначала в IndexedDB, UI отвечает мгновенно и сети не ждёт
- Pull при старте приложения (`GET /api/sync?since=lastSyncedAt`), затем push
  (`POST /api/sync`) — именно в этом порядке, иначе можно затереть локальной
  версией то, что параллельно пришло с другого устройства
- Push для `entries` — только помеченные `dirty: true` (записей может
  накопиться много за годы). Для `categories`/`tags` `dirty`-трекинг не
  заводили — их мало (десятки, не тысячи), проще каждый раз отправлять
  весь список целиком, сервер сам не перезапишет то, что не новее
- **`categories`/`tags` апсертятся одним массовым запросом**
  (`INSERT ... ON CONFLICT ... RETURNING`), не построчно. Раньше было
  select+insert/update на каждую строку — по два сабзапроса к Neon на
  элемент, и Cloudflare режет воркер на 50-м сабзапросе за запрос. 11
  разделов + 42 тега (обычный объём за пару недель ведения дневника, не
  какой-то экстремальный кейс) уже превышали порог: `POST /api/sync` падал
  с "Worker threw exception" **после** того, как разделы успевали
  записаться, но до `entries` — новые записи с телефона поэтому переставали
  доезжать вовсе, не только новые действия. Нашли по жалобе «синк не
  сработал», воспроизвели ровно на границе 50/51 строки суммарно. Массовый
  `ON CONFLICT` — один запрос на всю пачку вне зависимости от размера,
  проверено на 254 строках разом. `entries` пока остались построчно (там
  своя бизнес-логика на коллизию дат, см. ниже) — но их и так пушат только
  dirty, счёт обычно на единицы, а не на десятки
- Триггеры: старт приложения, `online`, `visibilitychange` (Background Sync
  API есть не везде, см. офлайн-таблицу ниже) — и сразу после любого
  локального сохранения/удаления, не только по таймеру
- Конфликты — last-write-wins по `updatedAt`, подробный разбор и известный
  trade-off — в «Офлайн-архитектуре» ниже
- На дату — ровно одна запись, и это держится с обеих сторон: в Dexie `date`
  уникален, в Postgres висит частичный уникальный индекс `(user_id, date)
  WHERE deleted_at IS NULL`. Один и тот же день, заведённый на двух
  устройствах независимо, даёт две строки с разными id — коллизию разводим
  тем же last-write-wins, проигравшую гасим мягко, чтобы удаление доехало до
  устройства-автора. Раньше такая коллизия обрывала транзакцию мёржа
  целиком, и устройство молча переставало синхронизироваться
- Смена аккаунта на устройстве отслеживается по `syncedUserId` в `settings`:
  если в сессии другой `userId`, локальный дневник и курсор `lastSyncedAt`
  стираются перед пуллом. Без этого чужие записи остаются в ленте, а курсор
  от прошлого аккаунта заставляет сервер отдавать только то, что новее чужой
  синхронизации — то есть почти ничего. Настройки внешнего вида при этом
  сохраняются: они и так не синхронизируются, это предпочтения устройства
- Почта аккаунта показана прямо в статусе синхронизации на всех экранах.
  Одного «Синхронизировано» мало: два устройства под **разными** аккаунтами
  оба пишут «Синхронизировано» и оба не врут (так и потеряли день работы)

  - Решили не тормозить из-за этой развилки календарь и статистику

## Визуальный стиль

Soft puffy 3D («пластилин») с пастельным фоном и точечным неоном. Собран
целиком на CSS: ни одной картинки, ни одного 3D-рендера — из референсов взята
пластика, а не содержимое.

**Глубина — это иерархия, а не украшение.** Если пухлое всё, стиль
разваливается в кашу, поэтому четыре ступени, и каждая означает роль:
`shadow-clay-1` — карточки, `-2` — контролы, `-3` — плавающее (таб-бар, «+»),
`-in` — нажатое. Пластилиновая тень — это всегда три тени сразу: внешняя мягкая
снизу плюс две внутренние, светлая сверху и тёмная снизу. Токены в `@theme`
(`src/style.css`), а не инлайном по компонентам.

**Нажатие меняет знак тени на внутреннюю.** Отмеченный тег физически
вдавливается (`shadow-clay-in`) — для переключателя «было / не было» это точнее,
чем просто заливка цветом.

**Неон означает ровно одно: «выбрано / сейчас».** Выбранный уровень настроения,
отмеченный тег, «+», активная вкладка, сегодняшний день. Больше нигде, иначе
выделение перестаёт что-либо выделять.

**Свечение считается из цвета элемента, а не задано константой** — цвета
настроений и разделов задаёт пользователь. Два нюанса, оба решены в `style.css`:

- *Бледные палитры.* От почти белого цвета неона не бывает, и на пастельной
  палитре свечение пропадало. Обводку как запасной вариант забраковали, поэтому
  стоит **пол по насыщенности**: `oklch(from var(--c) min(l,.72) max(c,.2) h)` —
  цвет плитки остаётся ровно тем, что выбрал пользователь, а светится она
  насыщенной версией того же тона. Под `@supports`: без относительных цветов
  свечение просто мягче, ничего не ломается
- *Картинка вместо эмодзи.* В картиночном наборе плитку закрывает непрозрачное
  изображение, и подсветить её изнутри нечем. Поэтому цвет вынесен **наружу**:
  `.halo` рисует ореол тенью за границей элемента и виден при любой картинке.
  Заливка цветом остаётся только для эмодзи-наборов

**Экран записи теплеет под выбранное настроение** (`.mood-ambient`). Светлоту
тона нормализуем, а не берём как есть: «Прекрасно» в классической палитре —
тёмно-зелёный, и прямой заливкой он ложился на пол-экрана грязным пятном.

**Карточка ленты тонируется цветом дня** (`.tint-day`, 16%). Слабо намеренно:
заметка — главный текст ленты, она обязана остаться тёмной на светлом. Подпись
уровня по этой же причине стала тёмной, а не цветной — на тонированной карточке
цветной текст сливался с фоном. Аватар настроения в карточке — квадратный
(`rounded-tile`), не круглый: тот же радиус, что у плитки в шкале настроения
на экране записи, форма настроения должна быть одинаковой везде.

**Фон приложения — градиентный меш из акцента**, а не независимого цвета
(`body::before`). Оба пятна считаются из `--accent`: второе — его аналоговый
оттенок через `oklch(from var(--accent) l c calc(h + 34))`, не отдельный
хардкод, иначе фон на лаймовом акценте спорил бы с оранжевым пятном. Мягкий и
не поверх контента: карточки в этом стиле почти всегда edge-to-edge, так что
меш проглядывает в зазорах и по краям экрана, а не расписывает сами карточки.

**Стекло — только на таб-баре.** Он единственный реально висит над
прокручивающимся содержимым. `backdrop-filter` на закреплённом элементе поверх
длинной ленты на старых айфонах ощутимо стоит — если поймаем просадку, откат на
плотный фон не затрагивает остального стиля.

**Цвет приложения** — настройка в «Больше», семь неоновых вариантов
(`src/lib/accents.ts`). Из выбранного цвета считаются два оттенка: неоновый
уходит в свечение, а под белый текст берётся затемнённый (`--accent-ink`). Иначе
белая подпись на лаймовом или голубом просто не читается — пришлось бы выкинуть
половину цветов. Амбиентный фон приложения ведёт за акцентом.

**Шрифт — Nunito**, вариативный 400–800, кириллица + латиница, 58 КБ, лежит в
`public/fonts` и попадает в прекэш. Не через `fonts.googleapis.com`: приложение
offline-first, и шрифт по сети означал бы, что без интернета оно открывается без
шрифта. Лицензия OFL — self-hosting разрешён. В запасной стек добавлен
`ui-rounded`: на айфоне это системный SF Pro Rounded, так что пластика уцелеет,
даже если файл почему-то не доехал.

**Тёмной темы нет.** Пластилин в тёмной теме собирается по другим правилам —
светлая внутренняя тень там не работает, — так что это отдельная задача, а не
побочный эффект.

## Модель данных — черновик

Таблицы `sessions` в итоге нет: сессия — не строка в БД, а подписанный JWT
(HS256 на WebCrypto, без зависимостей) в httpOnly-куке; сервер ничего не
хранит и не запрашивает на каждый чих. Цена — сессию нельзя отозвать
удалённо («выйти на всех устройствах» не завести без сессионной таблицы),
но для личного дневника это не критично, а простота перевешивает.

```
users
  id, email, createdAt

login_codes                   // код из письма, не ссылка — см. «Авторизация»
  id, userId, codeHash, expiresAt, usedAt, attempts, createdAt

login_code_requests           // только для rate-limit, фронтендом не читается
  id, email, ip, createdAt

user_settings                 // в схеме есть, в /api/sync пока не участвует —
  userId, activeMoodSetId, updatedAt   // активный набор настроений синкается
                                        // только локально (см. «Дальше»)

categories                  // разделы: Сон, Работа, Спорт…
  id, userId, name, color, sortOrder, archivedAt, updatedAt

tags                        // теги внутри раздела: Тренировка, Встречи…
  id, categoryId, name, icon, sortOrder, archivedAt, updatedAt

entries
  id, userId, date (YYYY-MM-DD, локальная дата), mood (1–7), note,
  createdAt, updatedAt, deletedAt

entry_tags
  entryId, tagId               // тег — просто отметка, значения нет
```

- `date` хранится строкой `YYYY-MM-DD`, а не timestamp: день — это календарная
  сущность в таймзоне юзера, а не момент времени. Уникальный индекс
  `(userId, date)` даёт правило «одна запись в день» на уровне БД
- Удаления везде мягкие (`deletedAt` / `archivedAt`) — иначе синк не сможет
  отличить «удалено на другом устройстве» от «ещё не доехало сюда»
- В IndexedDB (Dexie) `entries.tagIds` — плоский массив с multi-entry
  индексом вместо отдельной таблицы `entry_tags`: в локальном хранилище нет
  джойнов, массив на самой записи проще и быстрее для этого случая. На
  сервере (Postgres) join-таблица остаётся — при синке просто передаём набор
  `tagIds` целиком. Плюс локальное поле грязности записи для очереди синка

## Авторизация

Нужно простое решение с понятным восстановлением доступа. Решили: **код из
6 цифр на email через Resend**, без пароля — нечего забывать и восстанавливать,
вход и восстановление это один и тот же флоу.

Пароль обсуждали отдельно, специально из-за многоустройственности (нужно было
проверить, что вариант без пароля не хуже для входа на новом устройстве) —
и отклонили: восстановление пароля всё равно свелось бы к тому же коду на
почту, только вдобавок форма логина и хранение хеша. А на Cloudflare Pages
Functions нет нативного bcrypt/argon2 (не Node-рантайм), пришлось бы PBKDF2
через WebCrypto — решаемо, но лишний объём работы без выигрыша.

**Код, а не кликабельная ссылка (magic link) — решение задним числом, после
боевого прогона.** Сначала сделали классический magic link
(`GET /api/auth/verify?token=...`). На проде, при реальной отправке через
Resend, ссылка не открылась: Resend (использует AWS SES) заворачивает все
ссылки в письме в свой click-tracking редирект
(`https://r.<region>.awstrack.me/...`), и этот прокси-хост сам оборвал
соединение раньше, чем дошёл до нас — `daylens.kunitcan.online` при этом
отвечал нормально, проверяли напрямую. Час убили на дашборд Resend в поисках
тумблера, отключающего трекинг (он то не сохранялся, то требовал завести
отдельный tracking-поддомен с DNS-записью) — и он всё равно продолжал
заворачивать ссылку. У send-API Resend вообще нет параметра «без трекинга»
на конкретное письмо — это настройка на уровне домена в их дашборде, значит
мы зависим от того, что где-то там правильно потыкали галочки, и никак не
можем это проверить или починить кодом. Код на 6 цифр обходит проблему
целиком: нет URL — нечего заворачивать, нечего перехватывать сканерам
безопасности почтовых клиентов

- Таблица `users` заложена с первого дня (даже при одном пользователе) —
  добавить второго юзера потом = просто ещё одна строка
- Telegram-логин не делаем основным, но архитектурно не закрываем от себя
  возможность добавить как второй способ входа
- Passkey (Face ID) — рассматривали, отложили: требует отдельной библиотеки
  (например SimpleWebAuthn), таблицы credential'ов и WebAuthn-церемонии
  регистрации/входа — лишний слой сложности для первой версии. Можно добавить
  позже как апгрейд, ничего не переделывая
- Rate-limit на отправку кода закладываем с MVP (по IP и/или email) —
  защита от абьюза (спам чужих почт письмами) и экономия квоты Resend
  (100 писем/день)
- Код всего 6 цифр — короткий keyspace компенсируем: 15 минут жизни и
  блокировка после 5 неверных попыток ввода (`login_codes.attempts`)

## Push-уведомления

Не в MVP. Когда дойдём: нативный **Web Push API** (свой VAPID-ключ) вместо
Firebase — меньше внешних зависимостей, не завязано на Google-аккаунт. Firebase
(FCM) тоже сработал бы (с iOS 16.4+ он под капотом использует тот же стандарт
Web Push и работает в PWA, добавленной на экран), но смысла тянуть отдельный
Firebase-проект ради этого нет.

## Офлайн-архитектура — сводка

| Слой | Что кэшируется | Чем |
|---|---|---|
| App shell (UI) | HTML/CSS/JS, иконки | Workbox precache при установке |
| Данные | Все записи настроения | IndexedDB (Dexie) — пишутся сразу локально |
| Синхронизация | Очередь несинхронизированных записей | Background Sync API там, где есть, + fallback-ретрай на `online`/`visibilitychange` |
| Конфликты | last-write-wins по `updatedAt` | одновременное офлайн-редактирование одного дня на двух устройствах сознательно не решаем |

Приложение работает полностью автономно, сервер нужен только для
бэкапа/синхронизации, не для самой функции логирования.

Основной сценарий использования — iOS Safari, где Background Sync API не
поддерживается, поэтому fallback на `online`/`visibilitychange` — не опция,
а обязательный путь синка, а не просто подстраховка.

Известный и осознанно принятый trade-off (не временный, финальное решение):
две офлайн-правки одного дня на разных устройствах молча схлопнутся в
последнюю по `updatedAt` — потеряется, например, дописанная заметка.
Последовательное использование (правка → синк → правка на другом устройстве)
конфликта не даёт, только правда одновременное редактирование до синка.
Для одного пользователя это редкое совпадение, сложный merge ради него не
делаем.

### Бэкенд — сделано

6. **БД и схема** (Neon + Drizzle, `db/schema.ts`): `users`, `login_codes`,
   `login_code_requests`, `user_settings`, `categories`, `tags`, `entries`,
   `entry_tags`. Миграции через `drizzle-kit generate`/`migrate`, подключение
   через `@neondatabase/serverless` (не обычный `pg` — не работает в
   Workers-рантайме Cloudflare), паттерн из `english-lexicon-trainer`.
   `sessions` в итоге не завели — сессия стала stateless JWT (см. «Модель
   данных»)
7. **API авторизации** (`functions/api/auth/`): `request-code` (rate-limit —
   3/email и 8/IP за 15 минут, храним в `login_code_requests`, отдельная
   KV/Cloudflare-инфраструктура не понадобилась), `verify-code` (POST, код
   6 цифр, 15 минут жизни, до 5 попыток), `logout`, `/api/me`. Письма —
   прямой fetch к Resend API, без их SDK. Изначально был GET `/verify` по
   кликабельной ссылке — заменили на код после боевого прогона, см.
   «Авторизация» почему
8. **Экран входа** (`/login`): email → 6-значный код в той же форме, без
   перехода куда-либо. Вход **не блокирует** запись — офлайн и без сессии
   приложение продолжает писать в IndexedDB как раньше. На экране записи —
   статус в углу (не вошли / email + статус синка / ждут отправки: N)
9. **Синхронизация** (`functions/api/sync.ts` + `src/lib/sync.ts`): pull
   при старте, `online`, `visibilitychange` и сразу после каждого локального
   сохранения; push только `dirty`-записей (entries) и всех
   categories/tags целиком. Last-write-wins проверен вручную: более старый
   `updatedAt` отклоняется, более новый — принимается и перезаписывает
10. Полностью проверено вживую, включая один найденный и исправленный баг:
    первый вход на «новом» устройстве (свежий IndexedDB) дублировал
    разделы — локальный дефолтный сид срабатывает до входа (раньше просто
    не может знать, есть ли аккаунт), а первый pull после логина мёржил
    только что созданные дефолты с уже существующими на сервере вместо
    того чтобы их заменить. Фикс — `src/lib/sync.ts`: если это первый
    синк устройства (`lastSyncedAt` ещё нет) и сервер прислал непустые
    categories/tags, локальные полностью заменяются серверными, а не
    мёржатся по id. `entries` под это правило не попадают — это не
    дефолты, а реальные данные, если пользователь успел что-то занести
    офлайн до входа. Проверено сценарием «чистый браузер → вход в
    существующий аккаунт» до и после фикса, с проверкой количества строк
    и в Dexie, и напрямую в Neon

**Известный пробел:** настройки внешнего вида в `/api/sync` не участвуют и
живут только на своём устройстве — активный набор настроений
(`user_settings.activeMoodSetId`), активная палитра и сами свои палитры
(таблица `moodPalettes` есть только в Dexie, на сервере её нет), свои наборы
эмодзи (`moodEmojiSets`, туда же) и выбранный цвет приложения
(`activeAccentId`). То есть дневник между устройствами синхронизируется, а
«как он выглядит» — нет. Осознанно отложено, но с каждой новой настройкой долг растёт: разгребать
это стоит одним куском, добавив настройки и палитры в схему и в синк, а не
по одной штуке.

**Известный trade-off:** если локальные категории уже были отредактированы
(не тронутые дефолты) на устройстве, которое ещё ни разу не синкалось, и
только потом происходит вход в аккаунт с непустыми данными на сервере — эти
локальные правки будут заменены серверной версией по той же логике замены
на первом синке. Сценарий узкий (успеть покастомизировать офлайн строго до
первого входа в уже существующий аккаунт), сознательно не усложняем ради
него мёрж.
